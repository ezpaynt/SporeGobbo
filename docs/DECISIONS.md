## Change proposal and maintenance

For an enduring change, record: decision ID and current approved rule; requested behavior/ownership/dependency change; evidence; realistic alternatives including keep; affected systems/consumers/save schema/assets; risks, migration/recovery; exact validation and human review; owner approval reference; effective scope/date. Stop before production implementation or changing the documented authority.

A private extraction or local calculation fix that preserves authority, lifetimes and guarantees is not automatically architectural. If classification is genuinely unclear, explain the specific boundary at issue; do not request blanket approval or implement silently.

After approval, update affected architecture/contracts/testing, append a decision or explicit supersession link and report all doc changes. Preserve history; do not overwrite old failures or add a new ADR for every typo/bug. CURRENT_WORK holds transient status, not this record.
